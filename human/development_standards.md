# ForPrint Development Standards

## Призначення

Цей документ фіксує базові правила написання, оформлення і підтримки скриптів у ForPrint-проєктах.

Він не замінює локальні README окремих модулів, але задає єдиний стиль роботи для всієї екосистеми.

## Головний принцип

Код має бути не тільки робочим, а й зрозумілим для майбутнього супроводу.

```text
Через рік інший розробник або інший помічник має швидко зрозуміти:
- що робить скрипт;
- як його запустити;
- від чого він залежить;
- які файли створює або змінює;
- де шукати логи;
- що робити при помилці.
```
## Рівні застосування стандарту
### Рівень A — важливі production / integration / migration scripts

Для таких скриптів стандарт обов’язковий повністю.

Приклади:

міграції;
імпорт/експорт даних;
інтеграція з 1С;
генерація контрактів;
перевірка Blueprint;
генерація module guides;
складні training/evaluation scripts;
критичні backup/restore scripts.
### Рівень B — малі допоміжні scripts/tests

Для малих службових скриптів стандарт можна застосовувати скорочено:

зрозуміла назва;
короткий docstring;
валідація входів;
нормальний terminal output;
відсутність жорстких шляхів у тілі.
## Базова шапка важливого скрипта

На початку файлу має бути команда запуску:

# python -m package.path.to.module

Далі великий docstring:

📄 Назва
🧠 Призначення
🔗 Залежності
🗂 Шляхи / налаштування
🔍 Аудит і рекомендації
✅ Актуальність
📦 Пропозиції на майбутнє
▶️ Приклади запуску
## Імпорти

Порядок імпортів:

1. Стандартна бібліотека Python.
2. Сторонні бібліотеки.
3. Локальні модулі.

Локальні імпорти мають бути зрозумілими і стабільними. Не використовувати хаотичні sys.path, якщо цього можна уникнути.

Для скриптів, які запускаються напряму з директорії scripts/, допускається короткий bootstrap, якщо він уже прийнятий у проєкті.

## Шляхи і конфігурація

Жорсткі шляхи всередині тіла скрипта небажані.

Правильний порядок:

1. Константи з config.py або machine/*.yaml.
2. Константи на початку скрипта.
3. CLI-параметри.
4. Тільки як тимчасовий виняток — явний шлях у тілі з TODO у шапці.

Не видаляти старі константи з config.py без погодження.

## Валідація входів

Скрипт має перевіряти:

існування файлів;
існування директорій;
наявність потрібних ключів YAML/JSON;
наявність колонок CSV;
коректність enum/status значень;
діапазони числових параметрів, якщо вони є.

При проблемі — зрозуміле повідомлення українською або англійською, але без “тихого” продовження.

## Логування і terminal output

Важливий скрипт має показувати:

- що стартувало;
- які головні параметри;
- що перевірено;
- що створено/оновлено;
- де лежить результат;
- короткий підсумок.

Погано:

Скрипт тихо відпрацював, а користувач не розуміє, що сталося.

Добре:

✅ Blueprint validation passed
✅ Generated diagrams/module_graph.mmd
✅ Generated module_guides/calculator_engine.md
## Логи

Якщо результат роботи важливий для майбутнього аналізу, скрипт має писати лог або звіт у погоджену директорію.

Для Blueprint-проєкту базовий варіант:

reports/

Для окремих модулів — локальні logs/, reports/ або погоджені директорії конкретного модуля.

## Розмір скриптів

Не робити без потреби великі монолітні скрипти на 500–1000 рядків.

Бажаний орієнтир:

100–300 рядків для основної утиліти.

Якщо логіка росте — розносити по тематичних модулях.

## Дані і кодування

Усі текстові файли читати/писати як UTF-8.

Для CSV, які відкриватимуться в Excel, можна створювати додатковий файл:

*_utf8_bom.csv

Основний файл лишається чистим UTF-8.

## Заборона на самовільну зміну структури

Не переносити, не перейменовувати і не видаляти важливі директорії без погодження.

Якщо зміна структури потрібна:

1. Описати причину.
2. Запропонувати план міграції.
3. Дочекатися погодження.
4. Зробити малий контрольований крок.
5. Прогнати тести.
6. Закомітити.
## Doctor / Auto-repair

Ідеї Doctor / path-healer / auto-repair поки не реалізуються як активний механізм.

Поточний статус:

planned_optional_future_tool

Дозволено зараз:

документувати ідеї;
збирати вимоги;
проєктувати майбутній формат audit report;
робити пасивні перевірки.

Не дозволено зараз:

автоматично переписувати шляхи;
автоматично переносити файли;
автоматично видаляти “мертві” скрипти;
автоматично виправляти Makefile;
автоматично змінювати структуру без людини.
## Acceptance checklist

Перед комітом важливого скрипта:

- є зрозумілий запуск;
- є docstring;
- немає випадкових жорстких шляхів;
- входи валідовано;
- terminal output зрозумілий;
- результат записується у правильне місце;
- тести або smoke check проходять;
- структура проєкту не змінена без погодження.
