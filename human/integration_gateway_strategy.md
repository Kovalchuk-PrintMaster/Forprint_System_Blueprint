# ForPrint Integration Gateway Strategy

## Навіщо потрібен цей шар

Integration Gateway потрібен, щоб модулі ForPrint не перетворилися на щільно зшиту павутину прямих залежностей.

Він вирішує транспортно-контрактні задачі:

- приймає запити від сайту, Telegram Bot, CRM або іншого модуля;
- перевіряє payload за затвердженим контрактом;
- відсікає некоректні, неповні або підозрілі запити до того, як вони потраплять у предметний модуль;
- додає `correlation_id` і `idempotency_key`;
- маршрутизує запит у правильний модуль;
- повертає стандартизовану відповідь або помилку;
- формує audit events для Inspector.

## Що Gateway НЕ має робити

Gateway не є CRM, не є бізнес-оркестратором і не є джерелом предметної правди.

Він не має:

- вирішувати, чи вигідне замовлення;
- рахувати ціну;
- створювати канонічного клієнта або замовлення;
- резервувати матеріали власною логікою;
- формувати рахунок власною логікою;
- редагувати довідники Library;
- зберігати бізнес-історію як основне джерело правди.

## Правильна межа між CRM і Gateway

CRM відповідає на питання: **що треба зробити в бізнес-процесі?**

Gateway відповідає на питання: **чи коректний запит і куди його технічно передати?**

Наприклад:

1. CRM вирішила, що після підтвердження кошторису треба створити замовлення, зарезервувати матеріал і підготувати рахунок.
2. CRM формує `business_command`.
3. Gateway перевіряє команду за контрактом.
4. Gateway розкладає або маршрутизує її до Operational Registry, Warehouse і Accounting.
5. Gateway повертає CRM нормалізовані статуси.

## Приклад сценарію: сайт → калькулятор

1. Website створює `website_request`.
2. Website передає його в Gateway через `website_to_integration_gateway_request.v1`.
3. Gateway перевіряє обов'язкові поля: продукт, кількість, матеріал, формат, опції.
4. Якщо payload некоректний — Gateway повертає `validation_error`, і сайт показує клієнту зрозумілу відповідь.
5. Якщо payload коректний — Gateway створює `routed_module_request` для Calculator.
6. Calculator рахує результат.
7. Calculator повертає результат Gateway.
8. Gateway маршрутизує наслідки: CRM, Operational Registry, Warehouse, Accounting.

## Поступова реалізація

### Етап 1

Тільки Blueprint-рівень:

- описати модуль;
- описати data objects;
- описати контракти;
- описати потоки;
- генерувати module guide.

### Етап 2

Мінімальний Python/FastAPI сервіс:

- endpoint для прийому інтеграційних запитів;
- валідація JSON Schema / Pydantic;
- маршрутизація до mock adapters;
- стандартизована відповідь.

### Етап 3

Додати outbox/inbox:

- черга подій;
- retry;
- idempotency;
- audit log.

### Етап 4

Додати message broker, якщо система стане достатньо складною.

На старті не треба одразу Kafka/RabbitMQ. Для малого проєкту достатньо простого Gateway + чітких контрактів.
