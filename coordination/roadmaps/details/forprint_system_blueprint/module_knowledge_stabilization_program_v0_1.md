# Module Knowledge Stabilization Program v0.1

## Strategic thesis

The next roadmap-quality improvement is not achieved by generating more implementation tasks. It is achieved by reducing uncertainty about what already exists.

Capability discovery, document authority and module ownership must become explicit planning inputs.

## Program outcomes

Per selected module:
- Knowledge Index;
- Knowledge Base;
- document-authority map;
- capability reconciliation map;
- roadmap ↔ implementation linkage;
- cross-module reuse/migration candidates;
- cleanup work package;
- later, maintenance automation.

## Program phases

### Phase A — Library pilot
Manually prove the complete method.

### Phase B — normal module wave
Apply the refined method to:
1. Operations Control Registry
2. Accounting Registry Service
3. Integration Gateway
4. Logistics Service

### Phase C — high-risk legacy wave
Apply the hardened method to:
- Calculator Engine
- Telegram Bot

These modules require architecture-generation classification and strong conflict detection before cleanup.

### Phase D — portfolio expansion
Continue module by module according to Blueprint priority and roadmap need.

## Planning rule

A mature roadmap item should increasingly distinguish:
- Human Intent;
- historical evidence;
- current-state evidence;
- architecture decision;
- novelty (`REUSE / EXTEND / ADAPT / REPLACE / NEW`);
- module ownership;
- implementation state;
- roadmap maturity;
- reconciliation gate;
- execution readiness.

## Implementation gate

No new capability should move to implementation-ready merely because it appears absent from a quick repository search.

Existing, partial, duplicate, legacy and cross-module candidates must be checked first.
