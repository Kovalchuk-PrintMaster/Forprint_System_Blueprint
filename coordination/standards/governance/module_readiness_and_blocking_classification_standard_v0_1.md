# Module Readiness and Blocking Classification Standard v0.1

## Principle

A module can be known, planned and documented without being ready or necessary for active execution.

## Concept bootstrap

A future module is formally acknowledged when the project contains at least:

1. reserved module/project identity;
2. Blueprint module-description location;
3. basic purpose/value/boundaries;
4. initial capability skeleton;
5. provisional roadmap;
6. provisional dependency/blocking classification.

## Execution eligibility

Systematic module execution SHOULD NOT begin until sufficient knowledge exists for:

- Charter;
- Capability Catalog;
- target scope;
- meaningful roadmap;
- dependency placement;
- acceptance/evidence approach.

The required depth can be reduced for exploratory work, but exploratory status must be explicit.

## Blocking does not mean important

A strategically important module can be non-blocking today.

A support module can become phase-gate blocking later.

Classifications therefore require both **severity** and **time/stage**.

## Known initial classifications from the 2026-08-25 discussion

### forprint_system_administration

- non-blocking for current core development;
- likely future operational/workplace readiness gate before broad workstation/production rollout.

### forprint_marketing_orchestrator

- non-blocking for current core development;
- expected to become useful after business functionality can generate real commercial value.

All other classifications must be reviewed during the portfolio dependency exercise rather than
invented in this standard.
