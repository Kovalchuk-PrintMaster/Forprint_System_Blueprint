# Authority and coordination evolution

This is a derived historical narrative, not current runtime authority.

## 1. Early coordination doctrine
Blueprint begins as the balancing/architecture layer: keep modules synchronized, maintain global + module roadmaps, do not invent the next front, and preserve enough forward depth to avoid context-driven improvisation.

## 2. Operational surfaces become explicit
Makefile becomes the discoverable command map. Reporting, status, prompt and completion artifacts are progressively structured. Mutating operations are separated from read-only checks.

## 3. Completion is separated from acceptance
The v0.4 closed-loop design connects prompt → work → report → review → roadmap → next prompt, but later hardening makes an important distinction: completion/readiness is not acceptance/promotion.

## 4. Authority becomes fail-closed
Operator approval, pilot authorization, phase progression and global promotion become separate transitions. Later policy allows deterministic same-phase progression while keeping major phase boundaries manually controlled.

## 5. Current release becomes the front door
Historical continuity/roadmap artifacts are demoted from current authority. `coordination/releases/current.yaml` becomes the front door in the last-known reviewed baseline.

## 6. Logistics becomes the controlled automation pilot
The pilot narrows to Logistics only, with at least two successful real automatic prompt runs, positive stability review and a separate expansion decision before widening.

## 7. Runtime becomes pull-based and fresh-worker oriented
Blueprint publishes; module-side listener pulls; each substantial prompt gets a fresh worker with generated context, previous completion evidence, navigation and roadmap state.

## 8. Project memory becomes infrastructure
Human Intent, semantic inventory, repository knowledge, canonical startup, checkpoints, generated projections and the Assistant Handoff Compiler evolve from the original requirement to survive chat/context loss.

## 9. Automation safety becomes infrastructural
Mutation builder/validator/exact contracts evolve into fail-closed Mutation Compiler, explicit dependencies, clean-room checks, deterministic caches and lifecycle enforcement.

## 10. Remaining principle
Historical evidence can explain how the project reached its current design, but only a live repository audit can say what is implemented today.

## 11. Execution state separates from roadmap plan
The 12.09 continuation introduces Control Foundation. CF-02 explicitly treats the continuity event store as actual execution authority while roadmap position becomes a generated projection. This is a major refinement of the earlier roadmap/current-state drift problem; final migration is not proven complete in the source.
