# Strategic Transition Vector v0.1

**Status:** proposed temporary strategic direction  
**Authority:** directional context only. It does not override Project Constitution, canonical roadmap execution state, Work Front authority, execution profiles, governed procedures or continuity lifecycle.

## 1. Until the first internal Blueprint worker launches

The global/chat assistant should write code only for the minimum path required to launch the first internal worker.

Current launch path remains:

CF-08 → CF-09 → CF-10

Do not pull later convenience or self-hardening work in front of that path unless it is a real blocker.

## 2. After the first internal worker launches

Routine bounded Blueprint self-hardening should increasingly be assigned to that worker.

The global/chat assistant should concentrate on:
- deep audit and inventory of the other modules;
- conflicts, duplicates and obsolete surfaces;
- verified current state;
- final/target functional description of each module;
- full roadmap from current state to target;
- human-decision provenance;
- synthetic/provisional planning only where human intent is absent;
- cross-module dependencies and impacts.

## 3. Before broad autonomous module rollout

Build the portfolio model first:
- module priority;
- dependency ordering;
- readiness;
- balancing/catch-up waves;
- forward-development waves;
- first coordinated module-worker wave.

Only after this should broad module workers begin.

## 4. Early worker retry philosophy

Early pilots should have a looser but still bounded retry budget.

The initial goal is discovery:
- log tools/capabilities used;
- log procedure nodes;
- log failure fingerprints;
- log repair attempts;
- log repeated failures;
- log restart reasons and resume coordinates.

Do not tighten production retry limits before we have enough statistics. Hidden friction in the project should be discovered first, then fixed.

## 5. Direction for existing functionality

Future workers should increasingly use registered project capabilities/tools rather than directly editing canonical internals.

Target flow:

worker
→ capability describe/help
→ input validation
→ authority/policy gate
→ governed procedure
→ safe mutation
→ affected validation
→ result envelope

Protected canonical surfaces should eventually reject unauthorized direct writes and return an actionable message pointing to the required capability/tool.

## 6. Sunset

This document is temporary.

It becomes obsolete when the first coordinated multi-module worker wave has actually started under the portfolio/wave plan. Then it should be retired or replaced by steady-state portfolio operating policy.
