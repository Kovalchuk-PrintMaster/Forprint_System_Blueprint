## Proposed role

The assistant summarizes Control Plane as a separate strategic-governance layer concerned with:
- strategic goals;
- module priorities;
- autonomy;
- decision rights;
- owner checkpoints;
- impact reports;
- module action plans.

Proposed separation:
- Control Plane = strategy/governance/autonomy/priorities;
- Blueprint = architecture/ownership/contracts/boundaries;
- Inspector = factual-state verification;
- CRM = human-facing coordination/dashboard;
- domain modules = real execution.

This is historically useful because the later 14.07 Blueprint dialogue explicitly says a separate Strategic Control Plane should be represented.

## Proposed v0.1

Small file-based skeleton only:
- no API;
- no DB;
- no UI;
- no notifications;
- no agent automation;
- no integrations with other repos.

Machine surfaces include:
strategic goals, business principles, module priority map, autonomy levels, decision rights, impact rules, checkpoints, change requests, notification rules and module-report schema.

## Autonomy and checkpoints

The proposed autonomy model uses levels 0–5 with Level 5 forbidden.

Decision rights would state:
- what a module can do independently;
- what requires owner checkpoint.

The proposal also suggests impact analysis for strategy changes around:
- customer channels;
- pricing;
- 1C integration;
- order ownership.

## Proposed strategy workflow

`goals → impact rules → action plans → checkpoint reports → Blueprint update requests`

This is an early predecessor of later owner-checkpoint/manual-phase governance.

- launch Inspector;

- own API/UI/Telegram;
- operate real orders;
- own clients/payments/catalog/pricing;
- connect to 1C;
- run production actions.

That boundary is compatible with later foreign-repo/authority discipline.
